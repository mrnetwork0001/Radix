## The problem

When a popular npm package is compromised, the clock starts immediately. In the
TanStack worm this May, 84 malicious artifacts landed across 42 packages within
six minutes of the CI breach. The question every security team asks first is
not *"what does this package look like?"* - it is:

> **Which of our services are exposed, through which routes, and what do we pin
> to right now?**

That is a **reachability** question. Not a similarity question. Radix answers
it with graph traversal in HydraDB - and then goes one step further than
reachability: it prunes the answer down to what the **semver evidence** says
can actually be reached.

## What Radix does

| Capability | How |
|---|---|
| **Reverse transitive closure** | One bounded `DEPENDED_ON_BY*1..N` traversal returns every exposed package, service and lockfile, with the hop-by-hop infection routes from `algo.SSpaths` |
| **Version-exact precision** | The traversal over-approximates by design; a semver engine (verified against node-semver on 8,806 cases) then prunes dependents whose ranges cannot resolve the malicious version, and lockfiles pinning clean releases - showing exactly what was pruned and why |
| **Maintainer co-authorship sentinel** | Walks `Package → MAINTAINED_BY → Maintainer → MAINTAINS → Other_Package` to flag sister packages published inside the breach window by the same account - the second wave, invisible to per-package scanning |
| **Typosquat proximity radar** | Levenshtein + homoglyph neighbours of high-download packages, precomputed into `TYPOSQUAT_OF` edges (including Cyrillic look-alikes) |
| **Real ingestion** | Point it at any repo - CLI, or the console's **ADD REPO** button: lockfiles (npm/yarn/pnpm) → npm registry metadata → **OSV.dev advisories** → graph. Malicious (`MAL-`) advisories set compromise flags; ordinary CVEs only raise risk scores |
| **24/7 sentinel** | A daemon sweeps OSV on an interval and applies the delta to the graph - new compromises light up the console without anyone asking |
| **Remediation, for real** | Beyond the rendered diff: a real branch in a scratch clone, npm `overrides` applied, lockfile **regenerated by `npm --package-lock-only --ignore-scripts`** so integrity hashes come from the registry - pushed as a PR when a token is configured, dry-run otherwise |

## Answering the track's six questions

Track 2A names six questions. Each maps to a specific traversal, and each is
runnable against the live deployment.

| The question | How Radix answers it | On the demo graph |
|---|---|---|
| Which internal services are transitively exposed? | Reverse closure over the materialised `DEPENDED_ON_BY` edge, bounded at depth N | **7 of 20 services**, 3 tier-1 |
| Which version of the dependency introduced the vulnerability? | `Version` nodes carry `compromised_window`; `MAL-` advisories record the exact malicious releases on the Package as `mal_versions` | `4.28.0` (demo); `debug 4.4.2` derived from the real MAL advisory |
| Which applications resolved the compromised version while it was live? | `Lockfile -[:RESOLVED_IN]-> Version` pins, intersected with the versions inside the compromise window | **4 of 10 lockfiles** resolved `4.28.0` during the window |
| Which other packages share maintainers or infrastructure with it? | Two-hop `Package -> MAINTAINED_BY -> Maintainer -> MAINTAINS -> Package`, filtered to publishes inside the breach window | **3 sister packages** published within 48h by the same account |
| Are there likely typosquat packages nearby? | `TYPOSQUAT_OF` edges precomputed with Levenshtein + homoglyph normalisation | **6 candidates**, including a Cyrillic homoglyph |
| What is the complete blast radius? | The closure above, then **pruned by semver evidence** so the number reflects what can actually resolve the malicious version | **35%**, with 2 dependents excluded and the reason shown |

The third question is the one most tools skip, and the sixth is where Radix
goes furthest: a reachable dependent whose range cannot resolve the malicious
release is *not* exposed, and Radix says which ones and why.

## Why HydraDB - and what Radix would lose without it

A vector store answers *"what is semantically near this?"*. Supply-chain
containment needs *"what is reachable from this, and by which exact route?"* -
a different class of problem. Embedding `tanstack-query` returns packages that
*resemble* it; it will never tell you that `checkout-web` is compromised
through a five-hop chain it has no textual resemblance to.

| | Vector search | HydraDB traversal |
|---|---|---|
| Answers | "what looks similar" - ranked, approximate | "what is actually reachable" - an exact set |
| Transitive depth | not representable | native, `*1..6` in one statement |
| The infection route | lost | whole paths, ready to animate and audit |
| New edge arrives | re-embed, re-index | just a write |

Concretely, HydraDB does the work in every request:

- the **closure** is a single bounded variable-length traversal (`MATCH (victim {id: $pkg})-[:DEPENDED_ON_BY*1..6]->(x)`), the engine's share of which is a few milliseconds;
- the **infection animation** replays real paths from the native `algo.SSpaths` procedure, not choreography;
- the **maintainer walk** and **typosquat lookups** are fixed-length hops over the same graph;
- **namespaces** isolate the demo world (`radix`), live data (`radix/live`) and test scratch (`radix/test`) inside one engine, with prefix-scoped token authorization we verified by probe.

Remove HydraDB and the product loses its core loop: recomputing a transitive
closure in Python per request means loading the entire edge set per query, and
a vector or relational store cannot express the bounded multi-hop traversal at
all without recursive self-joins that grow with depth. The engine *is* the
feature; Python only scores what the traversal returns.

### Built against the engine's real contract

Radix was built by probing HydraDB first and writing code second. Every
constraint is documented with its probe in
**[docs/HYDRADB_CONTRACT.md](docs/HYDRADB_CONTRACT.md)**, including the ones
that shaped the architecture:

- **Variable-length traversal runs only forward from a fixed source id** - so
  Radix materialises inverse edges (`DEPENDED_ON_BY`, `MAINTAINS`) at write
  time, turning the reverse question into a forward traversal. 2× edge storage
  for an impossible query made fast.
- **The Cypher subset is deliberate**: no `IN`, no `CONTAINS`, `WITH` is
  pass-through, aggregates are `count/sum/avg/collect`. Radix splits work
  accordingly - traversal in the engine, scoring in Python - and computes
  typosquat distances at ingest time since the engine has no string functions.
- Boot requirements that are easy to get wrong (`user: "0:0"`,
  `RUST_MIN_STACK`, volumes mounted *at* the data paths), the exact batched
  `UNWIND` write forms, 62-bit relationship ids round-tripping bit-for-bit,
  and a 30 s admission-control cap discovered live.

The ingestion pipeline has its own frozen contract in
**[docs/INGEST_CONTRACT.md](docs/INGEST_CONTRACT.md)**, and the REST surface in
**[docs/API_CONTRACT.md](docs/API_CONTRACT.md)**.

## Architecture

```
┌────────────────────────────────────────────────────────────────────┐
│  React + Vite  ·  landing (/) + console (/app), code-split         │
│  force graph · threat radar · blast gauge · patch modal · ADD REPO │
└──────────────────────────────┬─────────────────────────────────────┘
                               │ REST /api/*
┌──────────────────────────────┴─────────────────────────────────────┐
│  FastAPI                                                           │
│  closure + version-exact refinement · maintainer risk · typosquats │
│  breach simulation · ingest jobs · PR engine (dry-run / push)      │
└─────┬──────────────────────────────┬───────────────────────────────┘
      │ OpenCypher over HTTP         │ ingestion pipeline
┌─────┴────────────────────┐   ┌─────┴───────────────────────────────┐
│  HydraDB                 │   │  lockfile parsers (npm/yarn/pnpm)   │
│  namespaces:             │◄──│  npm registry (ETag-cached)         │
│   radix       demo world │   │  OSV.dev advisories (MAL-aware)     │
│   radix/live  real data  │   └─────────────────────────────────────┘
│   radix/test  scratch    │         ▲
└──────────────────────────┘         │ every N minutes
                              ┌──────┴──────────────┐
                              │  sentinel (24/7)     │
                              └─────────────────────┘
```

**Graph schema.** Nodes: `Package` (name, ecosystem, is_compromised,
risk_score, downloads_weekly, mal_versions) · `Version` (semver, published_at,
compromised_window, package_id) · `Maintainer` (username, email,
key_fingerprint) · `Service` (name, repo_url, criticality) · `Lockfile`
(filename, commit_hash). Edges: `DEPENDS_ON` (constraint, is_dev) ·
`MAINTAINED_BY` (since) · `RESOLVED_IN` (resolved_version) · `TYPOSQUAT_OF`
(edit_distance, similarity_score) - plus the internal inverses
`DEPENDED_ON_BY` / `MAINTAINS` that make reverse traversal possible.

Nodes are keyed by partitioned integer ids (a raw id is self-describing -
`3_000_004` is always a Maintainer), the graph itself is the id registry for
re-ingestion, and relationship ids are deterministic 62-bit hashes so re-runs
merge instead of duplicating.

## Quickstart

**Requirements:** Docker, Python 3.12+, Node 18+.

```bash
git clone https://github.com/mrnetwork0001/Radix && cd Radix
make dev
```

One command: HydraDB up, demo graph seeded, API + dashboard running. Open
**http://localhost:5173** - the landing page; **Launch App** enters the
console at `/app`.

```bash
make up            # HydraDB via docker compose, waits for /readyz
make seed          # demo world (idempotent, deterministic)
make backend       # FastAPI on :8000 (demo namespace)
make frontend      # Vite on :5173
make verify        # end-to-end check

# Real data
make ingest TARGETS="/path/to/repo https://github.com/org/app"
make live-backend  # backend pointed at radix/live
make osv-sync      # one advisory sweep
make sentinel      # the 24/7 watcher, foreground
```

Or submit a repo from the console itself: **ADD REPO** (left rail) → paste a
git URL or local path → watch the ingest log stream → the graph refreshes.
The demo namespace politely refuses UI ingestion so the seeded world stays
reproducible; run `make live-backend` for the real-data console.

## Security posture

Radix analyses graphs; it does not run other people's code.

- Package scripts **never execute** - every npm invocation is
  `--package-lock-only --ignore-scripts`.
- The PR engine works in a scratch clone, never modifies the source checkout,
  never pushes to `main`, and scrubs the GitHub token from every error and log
  line (there is a test asserting it).
- Compromise flags come from OSV's malicious-package corpus (`MAL-`), kept
  distinct from ordinary CVEs - a vulnerability raises a risk score, only
  malice sets `is_compromised`.
- Version-exact pruning **fails open**: an unparseable constraint keeps a
  dependent flagged. A security tool must not silently narrow on bad data.

## Deploy

The production stack (HydraDB + API + sentinel + nginx frontend) ships in
[deploy/](deploy/README.md), built to **coexist on a busy VPS**: loopback-only
binding by default (`127.0.0.1:8090`, put your existing reverse proxy in
front), hard memory/CPU ceilings per container (~2.7 GB total), own network
and volumes, nothing shared with the host's other services.

The frontend alone (landing + console) also deploys to any static host -
`frontend/vercel.json` carries the SPA fallback; point its `/api` rewrite at
the VPS once the backend is public.
